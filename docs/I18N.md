## 2. Purpose

This document defines how the application supports English and Bahasa Indonesia without changing authentication, RBAC, device access, monitoring logic, or faucet-control behaviour.

The application shall provide:

- A language selector.
- Persistent locale preference.
- Translated interface text, statuses, alerts, validation messages, and accessibility labels.
- Locale-aware dates, times, and numbers.
- Stable canonical values in APIs, the database, audit logs, and device communication.

## 3. Scope

This specification covers the frontend language experience, translation files, locale persistence, formatting, canonical status mapping, error localisation, accessibility, testing, and implementation constraints.

It does not define sensor calibration, ESP32 firmware, hardware logic, MQTT topics, API field names, database column names, or automatic translation of user-generated content.


## 4. Supported Locales (I18N-REQ-001)

| Locale | Language | Native label | Status |
|---|---|---|---|
| `en` | English | English | Supported |
| `id` | Indonesian | Bahasa Indonesia | Supported |

Locale identifiers shall follow BCP 47-compatible conventions.

## 5. Default and Fallback Locale (I18N-REQ-002)

The default locale is `id` (Bahasa Indonesia).

The fallback locale is `en` (English).

The fallback locale shall be used when a key is missing, a stored locale is invalid, or a requested locale is unsupported. Raw translation keys shall never be shown to users.

## 6. Locale Selection Priority (I18N-REQ-003)

Approved locale selection precedence:

1. Authenticated user's saved profile preference (`preferredLocale`).
2. Valid locale stored in the non-prefixed session cookie (`locale`).
3. Mandatory initial language-selection gate (for unauthenticated visitors without a valid persisted locale).
4. Application default locale (`id`) / fallback locale (`en`).

The saved authenticated preference shall be authoritative after login.

## 7. Language-Selection Gate & Settings Placement (I18N-REQ-004)

### 7.1 Mandatory Initial Language Gate for Unauthenticated Visitors

For an unauthenticated visitor with **no valid persisted locale cookie**, the application shall not render the normal login, register, or account-status UI first. Instead, it shall render a small centered mandatory language-selection gate:

- `English` → `en`
- `Bahasa Indonesia` → `id`

The gate text shall be concise, bilingual, or language-neutral (`Select Language / Pilih Bahasa`) so it is understandable before a locale selection is made.

Upon selection:
1. Validate the locale (`id` or `en`).
2. Persist the selection using the non-prefixed cookie strategy (`locale`).
3. Render the requested authentication/public page in that locale.
4. Preserve existing non-prefixed routes.

If a valid locale cookie already exists, the application shall **skip the gate** and render the requested page directly.

### 7.2 Post-Entry Language Changes in Settings

After initial gate selection, subsequent language changes are available exclusively from the **Settings** page (`/settings`).

Language selectors shall **NOT** be placed on:
- application header;
- user menu dropdown;
- login or registration forms;
- mobile navigation drawers.

Language names shall be displayed in Settings as:

```text
English
Bahasa Indonesia
```

When a user changes language in Settings:

1. Validate the locale.
2. Update visible text without requiring logout.
3. Update the HTML `lang` attribute.
4. Preserve current page, selected device, and user context.
5. Persist selection (to profile for authenticated users, cookie for unauthenticated).
6. Reformat dates, times, and numbers.
7. Keep roles, permissions, and device access unchanged.
8. Use fallback locale (`en`) for missing keys.

## 8. User Profile Field (I18N-REQ-005)

| Field | Type | Allowed values | Default |
|---|---|---|---|
| `preferredLocale` | String | `en`, `id` | `id` |

An Admin may update only their own locale preference. An Owner may update their own locale preference.

## 9. Routing Strategy (I18N-REQ-006)

The approved routing strategy is **No Locale Prefix** (cookie-based non-prefixed strategy):

```text
/dashboard
/login
/register
/settings
```

The active locale is resolved via the non-prefixed cookie (`locale`) or authenticated profile preference (`preferredLocale`). URL path structures remain unchanged across languages.

## 11. Translation Key Rules

Keys shall be stable, descriptive, and namespaced.

Recommended examples:

```text
common.save
common.Manual Open/Close
common.confirm
auth.login.title
auth.account.pendingApproval
navigation.dashboard
soil.nitrogen
water.tankVolume
faucet.commandCompleted
users.pendingApprovals
validation.invalidEmail
errors.forbidden
```

Do not use full English sentences or component paths as keys.

All user-facing text shall use translation keys, including navigation, buttons, labels, forms, validation, toasts, status badges, tooltips, chart labels, table headings, dialogs, empty states, and accessibility text.

Dynamic values shall use interpolation rather than string concatenation.

Example:

```json
{
  "lastUpdated": "Last updated {time}",
  "deviceOffline": "Device {deviceName} is offline"
}
```

The following shall remain unchanged:

- Device IDs.
- Sensor IDs.
- User IDs.
- MQTT topics.
- API field names.
- Database field names.
- Audit event keys.
- Canonical enum values.
- Firmware versions.
- Coordinates.
- Raw measurement values.
- Technical abbreviations.

Technical abbreviations that shall remain unchanged include:

```text
N
P
K
pH
EC
TDS
ESP32
NodeMCU
MQTT
API
RBAC
GPS
mL

```

User-generated device names, notes, profile names, site names, approval notes, and acknowledgement notes shall not be automatically translated. Canonical `deviceId` strings (e.g. `water-node-001`) remain untranslated technical identifiers and are exposed only to Owner users; Admin users are presented only with localized default device type labels or custom device names per `DEC-DEV-028` (`TASK-0305`).

## 18. Date, Time, and Number Formatting

Timestamps shall be stored and transmitted in ISO 8601 or another approved machine-readable format.

Example:

```text
2026-07-27T13:45:00+07:00
```

The frontend shall format dates and times using the active locale and user timezone.

Changing language shall not automatically change timezone.

Recommended display examples:

| Context | English | Bahasa Indonesia |
|---|---|---|
| Date and time | 27 Jul 2026, 13:45 | 27 Jul 2026, 13.45 |
| Relative time | 5 minutes ago | 5 menit yang lalu |

Number formatting examples:

| Raw value | English | Bahasa Indonesia |
|---:|---|---|
| `1000` | 1,000 | 1.000 |
| `1.5` | 1.5 | 1,5 |
| `1234.56` | 1,234.56 | 1.234,56 |

Sensor precision shall follow the data contract. The I18N layer shall not invent precision.

Units shall be displayed consistently:

```text
300 mL (UI 0.3 L)
1.5 L
25 °C
60 %
```

## 20. Backend, Database, Device, and Audit Rules

The backend and database shall store canonical values such as:

```text
ACTIVE
COMPLETED
ONLINE
NORMAL
```

They shall not store translated display values as canonical state.

The device communication layer shall remain locale-neutral.

The following shall remain identical regardless of UI language:

- MQTT topics.
- Payload keys.
- Device commands.
- Command IDs.
- Device IDs.
- Acknowledgement fields.
- API request and response field names.

Example command payload:

```json
{
  "commandId": "cmd-001",
  "action": "DISPENSE",
  "phase": 2,
  "targetVolumeMl": 1000
}
```

Audit logs shall store canonical event keys such as:

```text
account.approved
device.access.assigned
faucet.command.completed
```

The frontend shall translate those event keys for display.

## 22. Translation Development Workflow (I18N-REQ-009)

1. Add the key to the default locale.
2. Add the same key to every supported locale.
3. Use the key in the component.
4. Validate interpolation placeholders.
5. Review the key in context.
6. Test desktop and mobile layout.
7. Test accessibility text.
8. Run translation completeness checks.

The automated CI process (`check-translations.ts` via `npm run i18n:check`) currently detects and prevents:

- Missing keys.
- Extra keys.
- Empty translations.
- Invalid placeholders.
- Duplicate keys.
- Raw untranslated keys.

## Monitoring Reconciliation & I18N Independence (Reconciled 2026-08-19)

The monitoring UUID and history regression fix (`TASK-0306`, `TASK-0501`, `TASK-0503`, `TASK-0504`) introduced zero new translation requirements or I18N changes:
- **Translation Consistency:** All existing translation namespaces (`soil`, `water`, `history`, `devices`, `common`, `errors`) and ICU placeholders remain fully intact and verified across `id.json` and `en.json`.
- **Untranslated Technical Identifiers:** Immutable database UUIDs (`devices.id`) and canonical `deviceId` strings remain unmutated and untranslated by localization hooks.
- **Frontend Device Selection:** Selected device identity consistently uses immutable database primary key `devices.id` UUIDs across English and Indonesian UI modes.
